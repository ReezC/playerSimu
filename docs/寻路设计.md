# 寻路设计（方案 / 数据格式 / 分期）

> 这份文档的目的：把「寻路」这件事**定下来**，以后（包括 AI 助手换会话、换人接手）
> 照着它就能继续做，不用重新讨论一遍。带 ✅ 的是**已在真资源上验证过**的事实，
> 带 ⚠ 的是**待验证**，带 ❌ 的是**明确不做**。

---

## 1. 目标与边界

**目标**：让角色在**一张已知地图**上自己走到指定位点（先同平台，再跨平台），
并据此把「找怪 → 靠近 → 打」的闭环从"原地打视野内的怪"扩展到"走到有怪的平台"。

**做**：
- 离线把地图地形（foothold / ladderRope / portal）与小地图底图从 WZ 导出来；
- 运行时用小地图上的**玩家黄点**换算出**世界坐标**，从而知道自己在地形图的哪一块；
- 在 foothold 连通图上找路，交给「按键执行器」走（左右走 + 跳跃，跳跃参数需先标定）。

**❌ 先不做**：绳梯/传送门的执行（数据先导出，逻辑后做）、多地图连续跑图、
怪物追击与寻路的融合（`chase` 仍是**纯水平**选目标 —— 2026-09-27 起的「攻击范围矩形」
（上下攻击距离）只管**攻击判定**，追击与追击起跳仍按水平距离 ✓）。

---

## 2. 方案评估（结论）

**采纳的整体思路**（这套方向是对的）：

1. 离线从 WZ 导出小地图 sprite + 地形布置；
2. 实时**单独推流**高分辨率小地图；
3. 在推流画面上定位小地图面板、模板匹配**黄点** → 世界坐标 → 与地形图对齐。

**要改的三处**（评估时发现的问题）：

### 2.1 缩放**不要靠人工标定** —— WZ 里有权威换算
✅ 实测 `105040303.img` 的根节点含 `miniMap`（与 `foothold`/`portal`/`ladderRope` 并列）。
参考实现 MapleNecrocer 的公式是硬编码 `/16`：

```
小地图像素 px = (世界坐标 X + centerX) / 16
              = (世界坐标 Y + centerY) / 16      ← MapleNecrocer\Client\UI\MiniMap.cs:373-374
```

它**没有读 `miniMap/mag`**（全仓 grep 无 `mag`），16 是它对 `mag` 的假设。
所以我们要**读 `miniMap/{centerX,centerY,mag,width,height}`**，用 `mag` 而不是 16 ——
这样「小地图像素 ↔ 世界坐标」是**算出来的**，不是标出来的。

于是「人工标定」退化成两件更小、且**一次/分辨率**的事：

- ① 小地图**面板在屏幕上的矩形**（框一次即可；换分辨率/换 UI 布局才需要重做）；
- ② 用一两个已知点**验证** `mag` 与底图是否 1:1 贴屏（是核对，不是试错）。

### 2.2 黄点的**三种画法**与已知误差
黄点的位置由客户端按上式算出（整数像素），画法有三种，匹配器都得认：

| 画法 | 素材/外观 | 参考 |
|---|---|---|
| WZ 素材 | `Map/MapHelper.img/minimap/user` | `MiniMap.cs:96,197,301,378` |
| 无素材兜底 | **5×5 青色方块** `Color(0,255,255)` | `MiniMap.cs:380-381` |
| 其它标记（要排除） | NPC 点 / portal 点 `Color(132,216,243)` | `MiniMap.cs:83-95` |

**误差**：`px = (int)(X + cx) / mag` 是**取整**的 → 世界坐标反推误差 **±mag 像素**
（`mag=16` 时约 ±16 世界像素）。够用来判断「我在哪一块 foothold 上」，
**不够**做精确落点 —— 落点仍靠跳跃标定 + 视觉闭环（见 §6）。

### 2.3 数据要**按 mapid 拆**，但别丢掉索引；foothold 要读全字段
- 现状：`datasets/maps.json` 一张大表（3677 张图 / 1997 有怪），**只有 id/名/地区/怪种，没有地形**。
- 改为：`datasets/maps.json` **保留为索引**（下拉列表要快），地形按图拆到 `datasets/map/<id>.json` + `<id>.png`（小地图底图）。
- ⚠ **`forbidDown` / `forceDown` 必须读**：MapleNecrocer 的 foothold 只读了
  `x1/y1/x2/y2/next/prev`（`Client/Footholds.cs`），而这两个字段决定
  **能不能从上往下跳**，寻路必需。

### 2.4 顺带发现的一块现成数据（建议用起来）
✅ `life` 里的怪刷新点带**巡逻范围**：`x / cy / rx0 / rx1`
（实测 `105040303` 有 48 条刷新点）。有了世界坐标，就能**直接算出"哪块平台上有怪"** ——
比纯视觉找怪稳得多，可以成为寻路的目标来源。

## 3. 三套坐标与换算

```
世界坐标 (X, Y)        帧原点：地图原点，向右 X+、向下 Y+；foothold/portal 用的就是它
     │  ÷ mag 后 +center
     ▼
小地图坐标 (px, py)     小地图底图 canvas 上的像素（0..width, 0..height）
     │  + 面板矩形在屏幕上的偏移（人工框一次）
     ▼
屏幕坐标 (sx, sy)       推流画面里的像素 —— 模板匹配/框选都在这个坐标系里
```

- 世界 → 小地图：`px = (X + centerX) / mag`，`py = (Y + centerY) / mag`
- 小地图 → 世界：`X = px * mag - centerX`，`Y = py * mag - centerY`
- 屏幕 → 小地图：`px = sx - panel_x0`，`py = sy - panel_y0`
- 世界 → 屏幕（游戏内，非小地图）：`屏幕 = 世界 - Camera`（参考 `Footholds.cs:204-212`）
  ⚠ **2026-09-27 起这条真的用上了**（反向的"画面 → 世界"）：用户要求"chase 要判怪位于的
  foothold 集合，不与玩家同一个就先下前往任务" ⇒ 而**怪只有画面坐标** ✗ ⇒
  `perception.minimap.screen_to_world(player, sx, sy)`（**全仓唯一一处**"画面 → 世界" ✓）
  用**玩家做锚**求出 Camera：`Camera = 玩家世界坐标 − 玩家画面坐标`（x 用框中心、y 用**框底**
  —— 世界坐标那套是"黄点脚底" ✓ 两边口径对齐 ✓）。
  ⚠ 那条公式**没有比例尺** ⇒ 它的前提就是「**画面 1 像素 = 世界 1 像素**」（推流按原始分辨率、
  没有缩放 ✓）。前提不成立时只是**刻度不对** ⇒ 调用方要把推出来的世界坐标**留痕**
  （note / 打点 ✓），别当精密测量用 ✗；实测精度参考上面那条"够判断在哪一块 foothold 上" ✓。
- ⛔ **给怪挑 foothold 必须放宽"面可以比它高多少"**（2026-09-28 现场：用户"**查#171 一个二楼的
  怪显示在底层，现在已经卡住了**"✗）。链条：`live_thread._resolve` 拿"**怪框底**"（`mob.y + h/2`
  ✓）经 `screen_to_world` 换成世界 y ⇒ 再用 `terrain.foothold_below` 找"脚下那条面"。
  ⚠ 而 `foothold_below` 的口径是按**玩家**定的：**面最多比给的 y 高 40**（`fy < y - tol` 就跳过 ✗）、
    往下不限、取 `|Δy|` 最小 ✓ —— 玩家的 "y" 是黄点脚底（就在面附近 ✓）所以没问题 ✓；
    可**大怪的检测框并不包住脚** ✗：实测那只二楼石人，**框底比它真正站的二楼面高 84px** ✗
    ⇒ 二楼那条面**直接被跳过** ⇒ 只剩"下方最近"的**一楼** ⇒ 怪被判到下一层 ✗
    ⇒ 追击下「前往一楼」，到了又判「底层」⇒ `mob_goto_ok 已出发：一楼 → 底层` /
    `底层 → 一楼` **来回卡死** ⟲（`chase_dist v=0.0` 一路刷）。
  ⇒ 修法：`foothold_below` 多一个 **`above_tol`**（`None` = 沿用 `tol` ⇒ **老行为一字不变** ✓）；
    `gui/live_thread.py` 给怪传 `MOB_ABOVE_TOL = 200.0` ✓。**比较仍然是 `|Δy|` 最小** ✓
    ⇒ 怪真站在一楼（框底就是脚）时一楼 `Δ≈0` 照样赢 ✓，**不会误伤** ✓。
  真数据（图 106010105，x=896 附近）：三楼 −178 / **二楼 −84** / 一楼 95 / 底层 185；
  `above_tol=40` ⇒ `fh=5 一楼` ✗、`above_tol=200` ⇒ `fh=22 二楼` ✓。
  用例：`selftest_minimap.t_foothold_below_prefers_nearer_within_xtol` ④⑤ ✓
  （④ 老口径仍判「一楼」+ 放宽后判「二楼」；⑤ 站在一楼上的怪不被抢走 ✓）。
- ⛔⛔ **"固定容差"这条路走不通 ⇒ 给怪挑面改成"它框覆盖的那一段"**（2026-09-28 用户：
  "**又把顶层怪判成底层怪了**"✗）。上面那条 `above_tol=200` 只撑了一天 ✗：
  **要害是层距** —— 实测图 **105040303** 的相邻层差 **540**（顶层 375 / 三楼 915 /
  二楼 1455 / 底层 1995 ✓）⇒ 固定值连**半层**都盖不住 ✗；
  而且只要"框底算出来的 y"偏过半层，`|Δy| 最小` 就**必然**挑到隔壁那层 ✗
  （扫描：框底偏差 300 ⇒ 固定容差给「三楼」✗）。
  ⇒ 口径换成 **候选面 = 怪框覆盖的那一段 y**（`band=(框顶世界 y, 框底世界 y)` ✓）：
    **怪一定站在"穿过它身体"的那条面**上 ⇒ 框底到底偏了多少**不用猜** ✓
    （扫描：偏差 ≤ 框高时**全对** ✓）。实现（`gui/live_thread.py::_resolve`）三级：
      ① 框覆盖段 ✓（主口径）；② 没有面 ⇒ **只往"上"放半个框高**再试 ✓
      （对"框底偏高、没包住脚"那一半有效；⛔ **绝不往下放** ✗ —— 往下会把**更近的错误层**

    `mapdata.foothold_below` 因此多了 `band=(lo, hi)` 参数（给了它就不看 `above_tol` ✓）；
    `above_tol` 保留，只在"连框高 / 世界坐标都拿不到"时兜底 ✓。
- ⭐⭐ **「向下垂线」那一级（用户 2026-09-28 的第三版口径 ✓）**："用 <玩家脚底到**怪框中心**的

**失败模式与降级**（都要显式处理，不能静默）：

| 情况 | 表现 | 处理 |
|---|---|---|
| 小地图窗口没开 / 被挡 | 找不到面板或底图对不上 | 报「无定位」，寻路整体不可用 → 停自动并提示 |
| 该地图没有 `miniMap` | 没有底图数据 | 报「这张图不支持寻路」（原来的"平台视觉对齐"兜底随平台识别一起移除了） |
| 换图/换频道 | 底图与实际不符 | 底图比对失败 → 重新确认地图，不要拿旧坐标跑 |
| 多玩家/多标记 | 匹配到多个候选 | 取与上一帧最近的一个（连续性）；连续丢帧才重锁 |

**对齐方式（按显示方式分成两条路，这是明确决定）**：

- **全局小地图（fit）→ 纯人工目测，不做自动标定** ✅
  实时情况下小地图**根本不动**，量一次就永久有效，没有任何"自动化"的必要。
  工作台「路线识别 → 小地图定位 → 标定…」：**选对参照图**（见下）→ 拖动/缩放
  让两层重合 → 保存。
  - ⚠ **透明度 0% = 叠图完全看不见**（2026-09-27）：0 是**合法的存档值**（设置那一侧
    专门修过"0 被 `or 55` 吃掉"的 bug），但一打开那扇窗就是"一片空白、像没标定过" ✗
    —— 用户报的"保存后再打开发现没保存"就是这个形状（他文件里 `alpha: 0`，几何明明存着）。
    ⇒ 那行读数**必须**写成「0%（叠图看不见）」，状态行也要说一句"几何是存着的，把透明度
    往右拖就能看见" ✓（见 `_sync_alpha_label`）。
  - ⚠ **两条缩放拖动条（x / y 各一条，各配一个数字框）**（2026-09-27 用户要求：
    「旧的标定弹窗应该有 2 个拖动条吧？x 和 y」）—— 两条分别对应 `scale` / `scale_y`，
    双点标定量出来的两轴几何可以在这里**分别**微调（以前只有一条，改的时候 y 按载入
    比例跟着走 ⇒ 比例只能在双点标定里改 ✗）；改哪条动哪条，保存照写 ✓。
    另一条老滑条是**透明度**（不改几何）。
  - ⚠ **2026-09-27 加了一条补充路径：「双点标定」**（§3 那一节）——它不只是"定量"，
    也是**核对**：填两对地标坐标解出几何后，能报"两轴一致不一致"、"按等比拟合的残差
    几像素"，这是模板匹配给不了的（它只报一个 `score`，而 score 只回答"像不像"）。
    两条路**写同一份标定**（按来源分开存），谁最后保存谁说了算。
  - ⚠ **2026-09-27 修**：「标定…」窗原来只认**一个**缩放 —— 叠加层按等比画、`calib()`
    连 `scale_y` 都不写 ⇒ 双点标定的两轴几何"打开看一眼、点一下保存"就被抹成等比 ✗
    （用户报的"双点标定完点开标定窗发现不太对"就是这个；顺带还把 `src` 降级成 `manual`、
    给没有匹配分的几何安上 `score: 0` ✗）。现在这扇窗**认两轴**：读进来、按两轴各自的
    缩放画叠加层（`QTransform`，不再是 `setScale`）、保存时原样写回；人拖动/改缩放时
    两轴**按同一比例**一起变（比例要改只能用「双点标定」重量一次）。**人没动过几何 ⇒
    保存时 `src`/`score` 也照抄载入的那份**（看一眼再保存不该改数据 ✓）。
  ⚠ **参照图选错就永远对不上**：客户端真用 WZ 的 `miniMap/canvas` 画小地图时叠
  「小地图底图」；**客户端按 foothold 现画**时（实测有些客户端就是这样：底图是
  白底绿棕、面板是黑底蓝地形，两套画）只能叠**「地形叠加图」** —— 平台形状一致，
  对着边缘就能目测对齐（弹窗里的「叠加参照」下拉就是干这个的）。
  - ⚠ **叠到实时画面那一层要按"标定当时那块面板"折算，而且折算比例算不出来时不许先画一版**
    （2026-09-26 用户报："叠加图的尺寸缩放在刚打开实时的时候是不正确的，要点一下
    路线识别页签才正常"）。标定记的是"**那块**面板像素 ↔ 底图像素"，而叠图要画在
    "**现在**框出来的那一块"上，两者可能差几倍（A 机推流带 zoom 时就是这样）⇒ 画之前
    先按 `标定面板 ÷ 当前那块` 折算（`perception/minimap.frame_overlay_rects` 的
    `calib_panel` 参数）。
    那个尺寸在来源=收流时只能问**当前收流帧**，而收流客户端是**懒建**的 ⇒ **第一次刷新
    必然拿不到** ⇒ 折算比例未知。**未知就先不画**（`route_panel._overlay_blocker` 里那条
    "等 A 机小地图推流来第一帧"）：画了就是错的（实测 251×189 糊在 134×109 的框上，
    宽 1.873 倍），而且画上之后 250 ms 那个节拍只在"还没挂上"时才整算 ⇒ **尺寸会冻结在
    第一次** ✗ —— 这正是"点一下页签才正常"（`showEvent → _refresh_mmap → _refresh_overlay`，
    那时早就有帧了）。
    拦下之后它靠那个节拍**自愈**：收流第一帧一到，250 ms 内画对（不用重标定、不碰标定文件）。
    用例：`t_overlay_waits_first_frame`（钉①帧没来不画且状态行说"在等第一帧"、
    ②帧来了自动画上且尺寸≈面板框 ③来源=从实时画面不许被这条拦住
    ④标定真对不上时把两个尺寸都摆出来）。
    反向验证过：去掉那条拦截 ⇒ 该用例当场红，报"折算比例还不知道就把叠图画上去了
    （尺寸必错）：(6, 72, 146, 380)"。
- **局部小地图（crop）→ 需要算法对齐，方案待定** ⚠
  面板只是一块、还会随人滚动，人工既对不准也看不全。候选（**后续再讨论**）：
  1. **地标法（首选方向）**：用面板里能找到、且**世界坐标已知**的东西做对应 ——
     传送点圆环 ↔ `portals`、绳梯 ↔ `ladderRope`、刷怪点 ↔ `life`……取 ≥2 个地标
     拟合相似变换（scale + offset），**残差大 = 认错了**，自带校验。
     ⚠ **难点**：每张图、以及同一张图里玩家所在位置不同，**能用的地标种类和数量
     都不一样**（有的图只有传送点、有的只有绳梯、有的一个都看不见）——所以"地标
     怎么检、拿哪几个去拟合"要单独设计，不能假定某一种一定在。
     - ✅ **2026-09-27：这条落地了**（`t_two_point_solve` / `t_two_point_dialog`）：
       「双点标定」= **走两个地方各采一次**（离线填那地方在地图上的坐标、实时按按钮读
       黄点脚底）→ 解相似变换 → 报两轴一致性与残差（§3 那一节）。**自动找地标**（上面
       那个"难点"）没做 —— 这条路上人只要走到地方、按一下按钮，不用在地图上找地标 ✓。
     - ⚠ 顺带一个**实算过的结论**：拿地图上的地标/位置**算不出「坐标系偏移」**（地标那层的
       "底图 ↔ 世界"由地图数据定死 ⇒ 反推恒为 0，死结论）。
     - ⚠ 2026-09-27 补：**采样（填脚底）与读数必须同口径** —— 原先定位读**重心**、采样填
       **脚底**，站回采样点读数差半个点高（现场 17 世界像素，见 §3 那段）。现在两边共用
       `perception.minimap.dot_feet`，「坐标系偏移」退化成"下沿 ↔ 原点"的残差（≈ 0）。
  2. 模板匹配（现有 `locate_crop`，已支持"放大后取块"）：只在客户端**确实用**
     `miniMap/canvas` 渲染时有效；遇到上面那种自己画的客户端，像素匹配怎么调都
     对不上（实测最高分 0.4，且是错位局部最优）❌。
  3. 按 foothold 渲染一张"客户端风格"的参考图再匹配（结构一致、配色不同）⚠。

**性能**：第二路解码很便宜（小图），但 B 机关键路径**已近 1 核、没有余量**
（见 `perf.log` 的性能评估）→ 上线前必须先量一遍两路同时跑时的 `proc_fps/over_budget`。

**同步**：黄点与主画面不是同一时刻 → 对"在哪块平台"无影响（±几十 ms），
但对"起跳到落点的精确时机"有影响 → 跳跃执行**只信主画面的视觉闭环**（§6），
小地图坐标只用来决定"去哪、走哪条路"。

## 6. 寻路与执行

**地形图**（离线数据 → 运行时可查询结构，新模块 `core/mapdata.py`）：

- `footholds` 按 `prev/next` 串成**段**（`PlatformID` 分组；参考 `Footholds.cs:256-271`）；
- 提供 `find_below(x) -> y`（脚下最近的 foothold，带直线插值；参考 `Footholds.cs:72-119`）、
  `segment_of(x, y)`、`neighbors(seg)`（连接关系：同一 `PlatformID` 相邻段、以及**可跳达**的段）；
- ⚠ 可跳达关系的判据（水平距离/高度差阈值、`forbidDown`）要在**标定出跳跃能力**之后才定得下来。

**执行器**（新模块 `decision/route.py`）：

| 动作 | 实现 | 依赖 |
|---|---|---|
| 走到 x | 按方向键，接近时点按微调 | 已有键控（`decision/input.py`） |
| 同平台跳（`jump`） | 走到边缘 → 按跳键 + 方向键（**初版执行器 2026-09-27 已做**，见下）| 落点预测（跳跃标定）—— 初版先用「起跳距离」这个**临时参数**顶上 ✓ |
| 下跳（`drop`） | **按住 ↓ 再按跳**（从平台上穿到下一层） | **跳跃标定** |
| 跨平台跳 | 走到边缘 → 起跳 → 空中用落点预测修正 | **跳跃标定**（落点预测随平台识别一起移除了，要做得先重新实现） |
| **上绳（`climb`）** | **定点**：对齐绳的 x → **按住跳** + ↑/↓ → 判定到达（`decision/route.py`）| **不用**跳跃标定（定点是"贴着绳按上去"，对时机不敏感）|

### 11.3 两个必须记住的实测结论

1. ~~`mag = 4`（不是 16）~~ **【已更正，2026-09-25 晚】** 上一版把

**术语：通行方式**（2026-09-26 定名）—— 两个集合之间"**怎么过去**"，就是它们的**通行方式**。

| `jump` | 跳(jump) | **站在边缘按跳键**（往前 / 斜着蹦） | — |
| `drop` | 下跳(drop) | **按住 ↓ 再点按跳**（往下穿；完整流程见上面「下跳」那一节 ✓） | — |
| ~~`portal`~~ | ~~传送门~~ | — | **2026-09-27 移除此通行方式** ✓ |

⚠ **`jump` 和 `drop` 别混**（用户专门澄清过）：一个是"**在边缘按跳**"往前蹦，
一个是"**按住 ↓ 再按跳**"往下穿。两者都要用跳键 ⇒ **执行**前必须先做**跳跃标定**（§6）；
但**记录不受影响** —— 先把"这里要跳 / 要下跳"标出来，标定完就能跑。

### 12.2 「同层（可走）」的判据 —— 有实测支撑

> **两条 foothold 同层** ⟺ 存在一处接缝：x 区间**相接或重叠**（`gap = 0`）**且**接缝处高度差 **`Δy = 0`**。
> **集合 A 与 B 同层** ⟺ 存在一对 `(f∈A, g∈B)` 满足上式。

`105090600` 实测（85 条横向 foothold、399 处候选接缝）：

| 判据 | 判为"同层可走"的接缝数 |
|---|---|
| Δy=0 且 gap=0 | **70** |
| Δy≤2 且 gap≤2 | **70**（一样） |
| Δy≤2 且 gap≤8 | **70**（一样） |
| Δy≤10 且 gap≤20 | 84 |

⇒ **数据是双峰的**（要么严丝合缝、要么差得明显），**阈值不敏感** ✅
⇒ 差 3~10 / gap 3~20 的那 14 处 ⇒ **只作建议**，编辑器里高亮接缝并显示 `Δx/Δy`，人工确认
⇒ 附加防护：接缝附近（x±一个身位）若有**竖向 foothold 横跨该 y**（墙挡着）⇒ 不算可走

- `plan_jobs` 的返回值多了 `costs`（每段选中那条边的代价 ✓，算不出来是 `None` ✓）——

- 用例：`selftest_zones.t_hop_cost_and_pick_edge`（跨类型也比 / 爬 = 距离+绳长 /

**2. 每一类边的「代价」= 纯距离，**不加动作惩罚**（用户 2026-09-27："不要动作惩罚" ✓）**

| 怎么过去 | "要花多远"怎么算（单位都是世界像素） |
|---|---|
| **走 `walk`** | **横向 + 垂直**：把目标平台上那几条落脚边**逐条算总代价、取最小的那条** —— 横向 = **max（我 → 那条边的左右距离, 我到「当前集合最近端点」的距离）**；垂直 = 高度差**原值（不打折）** |
| **跳 `jump`** | **横向 + 垂直**：横向 = 我 → 那条边的左右距离（**不加**上面的"当前集合端点"下限 —— 跳可以原地起跳 ✓）；垂直 = 高度差（**往下按折扣折算、往上原值** ✓） |
| **爬绳** | 两段相加：① 我从站的地方走到**入绳点**的**直线距离**（**上爬看绳的下端、下爬看绳的上端** —— 那才是真正要走到的地方，比拿绳中间算更贴近实际 ✓）；② **要爬的那段绳有多长**（爬得越高越贵 ✓）。⚠ **不打折** —— 爬上去、往下爬都不是"自然下落" ✓ |
| **下跳** | 两段相加：① 我到**离我最近的那个"允许下跳的落脚点"**的**横向距离**；② 从那个落脚点**掉到下面落点的高度差**（要落多深 ✓），**往下 ⇒ 按折扣系数折算** ✓（掉下去比走过去快得多 ✓）|

距离" + "所有的垂直下落端都要打折（下攀爬不是垂直下落）"）**：
· **`walk` 的横向有下限**：走到"目标那条面"其实**不一定够** —— 多层平台 x **大量重叠**，
  "我的 x 落在目标面的范围里"**不等于**"我这一层就能过去" ✗。原口径会把它算成 **0**，
  于是"楼上楼下"的 walk 假便宜。实测现场（`106010105`、**三楼 #91 → 二楼**）：玩家 x=836、
  二楼 fh=22 的 x 范围 `[738,902]` **罩住了他** ⇒ 横向 **0** ✗、垂直打 3.2 折 ⇒ walk 只有
  **29.4**，险胜 drop 的 **29.8** ✗ ⇒ 明明 drop 更近却选了 walk ✗。

  drop = **29.8** ⇒ **选 drop** ✓（人紧贴集合边缘时 walk=94 ⇒ 也还是 drop ✓）。
· **垂直折扣只给"真的会下落"的方式**：`jump` 往下 ✓、`drop` ✓；**`walk` / `climb` 一律原值** ✗
  （走路往下、往下爬都不是"自然下落"✓）。

⚠ **「自然下落折扣系数」= 3.2**（用户 2026-09-28 定）：**同样一段垂直距离，掉下去只相当于走 1/3.2** ✓
—— 掉下去比走过去 / 跳上去快得多；不折算的话，"从高处绕一格"会被算得跟"平地走一格"一样贵

⚠ 这是**内置的目标值**（用户："后续开发物理参数时再细化"）—— 等走速 / 跳 / 重力都能配了，
再换成**算出来的** ✓。⚠ **只有"往下"、且只有 jump/drop 才折算** ✓（见上 ⭐ 那条）。
⚠ 走 / 跳**必须逐条落脚边比"横向+垂直"的总代价**，⛔ 不能"先按横向挑最近的一条、再加它的高度"

（给改代码的人对照：走/跳 = `route.hop_cost` 里的 `_set_spans` + `_x_span_gap` ✓；

- 单位统一是**世界像素** ⇒ 天然可比 ✓（"走 3000px" 会输给"爬一段 500px 的绳" ✓ 这正是要的 ✓）；
- **算不了就不猜**：没有玩家位置（定位没输出）或几何缺失 ⇒ 那一类边按"不可算"处理，

**2.1 各执行器「自己」怎么算"到位没有"**（⚠ 与上面那张**择路**表**不是一回事**，别混 ✗）

|---|---|---|

| **追怪** | **画面上的横向距离**：角色中心 → 怪框最近的那条边。⚠ 这个是**画面像素**，不是世界坐标 | 攻击范围 / 追击范围 |
| **挑打哪只** | 先比"**走过去要多远**"（寻路距离 ≈ 上面那张表逐段加起来）；一样近才比画面距离 | 选目标（用户 2026-09-27："按**寻路距离**最近，而不是绝对距离"） |

⚠ 上面这些数（都在 `decision/route.py`；"对齐容差"另有项目设置可以覆盖 ✓）：
对齐容差 **10** 像素（走位 / 上绳共用）、点按微调与起跳 **20** 像素、"y 动没动" **8** 像素、
下跳落差兜底 **40** 像素、走"站上去"的高度差 **30** 像素。

⚠ **一个已知的重复**：算"横向间距"的那段代码**写了两遍**（择路那份 + 走那份）✗ ——
改这把尺得**改两处**，别只改一处 ✗。

**3. 并列 / 兜底的**裁决顺序**（顺序化 ⇒ 同输入同输出 ✓）**
① 代价小的；② **到目的地剩余段数少的**（段数少 = 失败点少 ✓）；③ 类型优先级
（`zones.KIND_PRIORITY`：走 > 爬 > 下跳 > 传送门 > 待确认 > 跳 ✓）；④ **文件顺序**（不猜 ✓）。

**4. 与现状的差别（落地时要改的）**
- `zones.find_path`（无权 BFS）从"**决定路径**"退成"**可达性剪枝 + 兜底**"；
- `route.pick_edge` 的"硬性类型优先级"→ 换成"**代价比较**"（同一段内多条边走边（`dir` 左/右）、
  多根绳、多个下跳点，全用**同一把尺** ✓ —— 现在只有"爬"会挑最近的 ✗）；
- 传送门 / 算不出的边：从"整条不下发" → "**这条不参选，换别的路**" ✓；
- 面板那行（`plan_jobs` 的 `path` / `edges`）显示的就是**贪心选出来的途径点** ✓，
  并（新增）带上**每段代价** ⇒ 一眼看出"为什么走这条" ✓。

**（原口径，仍作为兜底保留）**：类型优先级 `KIND_PRIORITY`（走 > 爬 > 下跳 > 跳 ✓ ——
`portal` / `unconfirmed` 2026-09-27 起**已彻底移除** ✗）+ 同类多条时按**到入绳点最近**
挑绳 + **算不了就文件顺序** ✓（`pick_edge` / `hop_cost` 都在 `decision/route.py` ✓；
位置从 `plan_jobs(..., at=(x, y))` 来 ✓）。

⚠ **位置从哪来**：`plan_jobs(..., at=(x, y))` 由调用方给 —— 面板给"最近一次定位读数"
  （`route_panel._world_at`，`_tick_world` 每 250ms 写）、实时线程给 WorldState
  （`live_thread._player_at`，和 `_player_here` 同一个地方写；定位没输出时**清空** ⇒
  退回文件顺序，不拿旧位置猜 ✗）。
⚠ **显示必须和实际执行一致**：`plan_jobs` 的返回值里带 `edges`（**实际选中的那些边**），
  「命令前往」那行用 `zones.edge_text(z, a, b, edge=那条)` 显示 —— 否则会出现
  "说着爬 L3、实际爬 L7" ✗（这种不一致最容易被当成 bug 报回来）。

**两条实测结论（都是"判据看着对、实际判空"那种，值得留档）**

1. **绳端离平台差几十像素是常态**：`105090600` 实测 L1(x=56) 上端 44px、L2(x=701) 49px、
   L3(x=1245) 43px ⇒ 用 `ATTACH_PAD(24)` 当 y 容差时**每根绳的顶端都落空**，
   `climb` 边恒为 0 条（看着像"集合没圈对"）。
   ⚠ **但容差不能乱放**（当天就踩了一次）：把它放到 60px 之后，选「右下」（y=280 那块
   大平台）时**下面两根绳全亮了**（L2 顶端 231、L3 顶端 237，y 区间根本碰不到它；
   它们其实是「右下休息平台」的绳）。⇒ **两个问题两套判据**：
   · 「这根绳**属于谁**」（空间归属 → 编辑器高亮）= `ladders_of`，**严格**（±ATTACH_PAD）；
   · 「爬上它**能不能到上面**」（连通性 → 建议）= `ladder_ends` / `climb_suggestions`，
     **宽松**（绳端差几十像素也算）；
   · 「加爬升边时选哪根绳」= `ladders_touching`（上面两者的并集）。
2. **传送门的落点数据是有的**：`Portal.tm`（目标图号，`999999999` = 本图内）+ `Portal.tn`（目标门名）。
   但本图 8 个门里 **6 个是 `pt=0` 出生点**、2 个是**跨图**（`tm=105090500/105090700`）
   ⇒ 本图回位**一条 portal 边都不该有**（`portal_suggestions` 返回 0 条是对的，不是坏了）。
   `pt=0` 必须排除，否则会把出生点当成门。
