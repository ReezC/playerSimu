# 寻路设计（方案 / 数据格式 / 分期）

> 这份文档的目的：把「寻路」这件事**定下来**，以后（包括 AI 助手换会话、换人接手）
> 照着它就能继续做，不用重新讨论一遍。带 ✅ 的是**已在真资源上验证过**的事实，
> 带 ⚠ 的是**待验证**，带 ❌ 的是**明确不做**。

---

## 1. 目标与边界

**目标**：让角色在**一张已知地图**上自己走到指定位点（先同平台，再跨平台），
并据此把「找怪 → 靠近 → 打」的闭环从"原地打视野内的怪"扩展到"走到有怪的平台"。

**做**：
- 离线把地图地形（foothold / ladderRope / portal）与小地图底图从 WZ 导出来；
- 运行时用小地图上的**玩家黄点**换算出**世界坐标**，从而知道自己在地形图的哪一块；
- 在 foothold 连通图上找路，交给「按键执行器」走（左右走 + 跳跃，跳跃参数需先标定）。

**❌ 先不做**：绳梯/传送门的执行（数据先导出，逻辑后做）、多地图连续跑图、
怪物追击与寻路的融合（现有 `chase` 是纯水平，先不动）。

## 2. 方案评估（结论）

**采纳的整体思路**（这套方向是对的）：

1. 离线从 WZ 导出小地图 sprite + 地形布置；
2. 实时**单独推流**高分辨率小地图；
3. 在推流画面上定位小地图面板、模板匹配**黄点** → 世界坐标 → 与地形图对齐。

**要改的三处**（评估时发现的问题）：

### 2.1 缩放**不要靠人工标定** —— WZ 里有权威换算
✅ 实测 `105040303.img` 的根节点含 `miniMap`（与 `foothold`/`portal`/`ladderRope` 并列）。
参考实现 MapleNecrocer 的公式是硬编码 `/16`：

```
小地图像素 px = (世界坐标 X + centerX) / 16
              = (世界坐标 Y + centerY) / 16      ← MapleNecrocer\Client\UI\MiniMap.cs:373-374
```

它**没有读 `miniMap/mag`**（全仓 grep 无 `mag`），16 是它对 `mag` 的假设。
所以我们要**读 `miniMap/{centerX,centerY,mag,width,height}`**，用 `mag` 而不是 16 ——
这样「小地图像素 ↔ 世界坐标」是**算出来的**，不是标出来的。

于是「人工标定」退化成两件更小、且**一次/分辨率**的事：

- ① 小地图**面板在屏幕上的矩形**（框一次即可；换分辨率/换 UI 布局才需要重做）；
- ② 用一两个已知点**验证** `mag` 与底图是否 1:1 贴屏（是核对，不是试错）。

### 2.2 黄点的**三种画法**与已知误差
黄点的位置由客户端按上式算出（整数像素），画法有三种，匹配器都得认：

| 画法 | 素材/外观 | 参考 |
|---|---|---|
| WZ 素材 | `Map/MapHelper.img/minimap/user` | `MiniMap.cs:96,197,301,378` |
| 无素材兜底 | **5×5 青色方块** `Color(0,255,255)` | `MiniMap.cs:380-381` |
| 其它标记（要排除） | NPC 点 / portal 点 `Color(132,216,243)` | `MiniMap.cs:83-95` |

**误差**：`px = (int)(X + cx) / mag` 是**取整**的 → 世界坐标反推误差 **±mag 像素**
（`mag=16` 时约 ±16 世界像素）。够用来判断「我在哪一块 foothold 上」，
**不够**做精确落点 —— 落点仍靠跳跃标定 + 视觉闭环（见 §6）。

### 2.3 数据要**按 mapid 拆**，但别丢掉索引；foothold 要读全字段
- 现状：`datasets/maps.json` 一张大表（3677 张图 / 1997 有怪），**只有 id/名/地区/怪种，没有地形**。
- 改为：`datasets/maps.json` **保留为索引**（下拉列表要快），地形按图拆到 `datasets/map/<id>.json` + `<id>.png`（小地图底图）。
- ⚠ **`forbidDown` / `forceDown` 必须读**：MapleNecrocer 的 foothold 只读了
  `x1/y1/x2/y2/next/prev`（`Client/Footholds.cs`），而这两个字段决定
  **能不能从上往下跳**，寻路必需。

### 2.4 顺带发现的一块现成数据（建议用起来）
✅ `life` 里的怪刷新点带**巡逻范围**：`x / cy / rx0 / rx1`
（实测 `105040303` 有 48 条刷新点）。有了世界坐标，就能**直接算出"哪块平台上有怪"** ——
比纯视觉找怪稳得多，可以成为寻路的目标来源。

## 3. 三套坐标与换算

```
世界坐标 (X, Y)        帧原点：地图原点，向右 X+、向下 Y+；foothold/portal 用的就是它
     │  ÷ mag 后 +center
     ▼
小地图坐标 (px, py)     小地图底图 canvas 上的像素（0..width, 0..height）
     │  + 面板矩形在屏幕上的偏移（人工框一次）
     ▼
屏幕坐标 (sx, sy)       推流画面里的像素 —— 模板匹配/框选都在这个坐标系里
```

- 世界 → 小地图：`px = (X + centerX) / mag`，`py = (Y + centerY) / mag`
- 小地图 → 世界：`X = px * mag - centerX`，`Y = py * mag - centerY`
- 屏幕 → 小地图：`px = sx - panel_x0`，`py = sy - panel_y0`
- 世界 → 屏幕（游戏内，非小地图）：`屏幕 = 世界 - Camera`（参考 `Footholds.cs:204-212`）

## 4. 离线数据（WZ → 文件）

**导出器**：在 `E:\MyPrograms\RippleRogue\MapleNecrocer\WzProbe` 加子命令
`dump-terrain <wzDir> <outDir> [--only id1,id2] [--minimap-only]`。
直接套用 `MapDump.cs` 的骨架（遍历 `Map.wz` → `TryExtract` → 组对象 → `System.Text.Json`）。

**地图 img 路径**：✅ 本套资源命中 `Map/Map/Map{首位数字}/{mapid}.img`
（如 `105040303` → `Map/Map/Map1/105040303.img`）。老资源可能没有 `Map1..Map9`
分目录（走 `Map/Map/{id}.img`），`MapDump.cs` 已有兼容分支，照抄。

**输出**：`<outDir>/<mapid>.json` + `<outDir>/<mapid>.png`（小地图底图，没有则跳过）

```jsonc
{
  "id": "105040303",
  "info": { "mapName": "…", "VRLeft": -1000, "VRTop": -2000, "VRRight": 3000, "VRBottom": 3000 },
  "miniMap": {                      // 可能整块不存在（老图）
    "canvas": "105040303.png",      // 单独落盘的底图
    "width": 200, "height": 200,
    "centerX": 1000, "centerY": 1500,
    "mag": 16                       // ⚠ 必须读；缺省按 16
  },
  "footholds": [                    // Map/Map{1}/<id>.img/foothold/{layer}/{group}/{idx}
    { "layer": 1, "group": 3, "id": 5,
      "x1": -100, "y1": 500, "x2": 300, "y2": 500,
      "next": 6, "prev": 4,
      "forbidDown": 0, "forceDown": 0 }
  ],
  "portals": [
    { "pn": "sp", "pt": 0, "x": 100, "y": 480, "tm": 0, "tn": "" }
  ],
  "ladderRope": [
    { "x": 250, "y1": 300, "y2": 520, "l": 1, "uf": 0, "page": 0 }
  ],
  "life": [                         // 与 maps.json 的 mobs 信息互补：这里有坐标与巡逻范围
    { "type": "m", "id": "3230100", "x": 165, "cy": 1455, "rx0": -328, "rx1": 598 }
  ]
}
```

**老版（0.75）注意**（✅ 已实测 / 参考 `WzUtils.cs`、`MapleMap.cs`、`MiniMap.cs` 的兼容分支）：

- `miniMap` **可能整块缺失** → 导出器必须容错（否则读 `canvas` 直接抛异常），JSON 里省略该键；
- `String.wz` 可能不存在 → 地图名从 `info/mapName` 读（`MapDump.cs` 已这么做）；
- `life.type` 老写法是 `"m"/"n"`（甚至 `"1"/"0"`）→ 不能只认 `"mob"`；
- 全量导出的**体积/耗时**要预估：3677 张图，地形 JSON 每张几十 KB 量级 → 总量百 MB 级，
  导出耗时分钟级到十几分钟（`TryExtract` 逐张解压是瓶颈）。

## 5. 实时定位（第二路小地图流 → 世界坐标）

**输入**：A 机**单独推流**的小地图区域（建议独立 URL/端口，分辨率按小地图面板 1:1 或整数倍）。
好处：不受主画面遮挡、不受编码缩放影响、模板匹配更稳。

**流程**（新模块 `perception/minimap.py`）：

1. 面板定位：在小地图流里定位底图 canvas 的矩形（首次人工框一次 → 之后可用模板匹配自动跟踪）；
   ——实现落点：A 机在「被控机部署台 → 小地图推流」里框（不用敲命令）；
   B 机在工作台「路线识别 → 小地图定位 → 标定…」里量（gui/minimap_calib.py：
   实时面板 + 半透明底图叠加，自动定位为主、手动拖动对齐为备；判据是"看得见的重合"）；
   ——画面来源两种（工作台「小地图来源」，存 config/live.yaml 的 mmap_src）：
   `收流` = A 机那一口独立推流（默认，原始像素）；`从实时画面框选` = 在实时那一帧上
   裁一块（B 机本地实验做法，mmap_crop 记区域）—— 省掉 A 机一次截屏 + 一路 TCP，
   但画面是 H.264 压过的：面板↔底图匹配没问题，**黄点识别能不能稳还没实测**；
2. 底图确认：与 `datasets/map/<id>.png` 比对（确认"现在这张图"就是项目选的那张，避免换图/换频道时张冠李戴）；
3. 黄点匹配：在面板内找 `user` 标记（素材模板 → 兜底 5×5 青色方块；排除 NPC/portal 点）；
4. 换算：`X = (px - panel_x0) * mag - centerX`（Y 同理）；
5. 输出：`WorldPos(x, y, t, conf)` 进 `WorldState`，供寻路/调试可视化用。

**失败模式与降级**（都要显式处理，不能静默）：

| 情况 | 表现 | 处理 |
|---|---|---|
| 小地图窗口没开 / 被挡 | 找不到面板或底图对不上 | 报「无定位」，寻路整体不可用 → 停自动并提示 |
| 该地图没有 `miniMap` | 没有底图数据 | 报「这张图不支持寻路」（原来的"平台视觉对齐"兜底随平台识别一起移除了） |
| 换图/换频道 | 底图与实际不符 | 底图比对失败 → 重新确认地图，不要拿旧坐标跑 |
| 多玩家/多标记 | 匹配到多个候选 | 取与上一帧最近的一个（连续性）；连续丢帧才重锁 |

**对齐方式（按显示方式分成两条路，这是明确决定）**：

- **全局小地图（fit）→ 纯人工目测，不做自动标定** ✅
  实时情况下小地图**根本不动**，量一次就永久有效，没有任何"自动化"的必要。
  工作台「路线识别 → 小地图定位 → 标定…」：**选对参照图**（见下）→ 拖动/缩放
  让两层重合 → 保存。
  ⚠ **参照图选错就永远对不上**：客户端真用 WZ 的 `miniMap/canvas` 画小地图时叠
  「小地图底图」；**客户端按 foothold 现画**时（实测有些客户端就是这样：底图是
  白底绿棕、面板是黑底蓝地形，两套画）只能叠**「地形叠加图」** —— 平台形状一致，
  对着边缘就能目测对齐（弹窗里的「叠加参照」下拉就是干这个的）。
- **局部小地图（crop）→ 需要算法对齐，方案待定** ⚠
  面板只是一块、还会随人滚动，人工既对不准也看不全。候选（**后续再讨论**）：
  1. **地标法（首选方向）**：用面板里能找到、且**世界坐标已知**的东西做对应 ——
     传送点圆环 ↔ `portals`、绳梯 ↔ `ladderRope`、刷怪点 ↔ `life`……取 ≥2 个地标
     拟合相似变换（scale + offset），**残差大 = 认错了**，自带校验。
     ⚠ **难点**：每张图、以及同一张图里玩家所在位置不同，**能用的地标种类和数量
     都不一样**（有的图只有传送点、有的只有绳梯、有的一个都看不见）——所以"地标
     怎么检、拿哪几个去拟合"要单独设计，不能假定某一种一定在。
  2. 模板匹配（现有 `locate_crop`，已支持"放大后取块"）：只在客户端**确实用**
     `miniMap/canvas` 渲染时有效；遇到上面那种自己画的客户端，像素匹配怎么调都
     对不上（实测最高分 0.4，且是错位局部最优）❌。
  3. 按 foothold 渲染一张"客户端风格"的参考图再匹配（结构一致、配色不同）⚠。

**性能**：第二路解码很便宜（小图），但 B 机关键路径**已近 1 核、没有余量**
（见 `perf.log` 的性能评估）→ 上线前必须先量一遍两路同时跑时的 `proc_fps/over_budget`。

**同步**：黄点与主画面不是同一时刻 → 对"在哪块平台"无影响（±几十 ms），
但对"起跳到落点的精确时机"有影响 → 跳跃执行**只信主画面的视觉闭环**（§6），
小地图坐标只用来决定"去哪、走哪条路"。

## 6. 寻路与执行

**地形图**（离线数据 → 运行时可查询结构，新模块 `core/mapdata.py`）：

- `footholds` 按 `prev/next` 串成**段**（`PlatformID` 分组；参考 `Footholds.cs:256-271`）；
- 提供 `find_below(x) -> y`（脚下最近的 foothold，带直线插值；参考 `Footholds.cs:72-119`）、
  `segment_of(x, y)`、`neighbors(seg)`（连接关系：同一 `PlatformID` 相邻段、以及**可跳达**的段）；
- ⚠ 可跳达关系的判据（水平距离/高度差阈值、`forbidDown`）要在**标定出跳跃能力**之后才定得下来。

**执行器**（新模块 `decision/route.py`）：

| 动作 | 实现 | 依赖 |
|---|---|---|
| 走到 x | 按方向键，接近时点按微调 | 已有键控（`decision/input.py`） |
| 同平台跳（`jump`） | 走到边缘 → 按跳键 + 方向键 | **跳跃标定** |
| 下跳（`drop`） | **按住 ↓ 再按跳**（从平台上穿到下一层） | **跳跃标定** |
| 跨平台跳 | 走到边缘 → 起跳 → 空中用落点预测修正 | **跳跃标定**（落点预测随平台识别一起移除了，要做得先重新实现） |
| **上绳（`climb`）** | **定点**：对齐绳的 x → **按住跳** + ↑/↓ → 判定到达（`decision/route.py`）| **不用**跳跃标定（定点是"贴着绳按上去"，对时机不敏感）|

**定点上绳已经做了**（2026-09-26，用户确认"可以先做"）：

```
① 移动到 |x − 绳.x| ≤ 「坐标对齐误差范围」，并保持「坐标对齐误差时间」那么久
② 按住跳 + 按住 ↑（向上）或 ↓（向下）
③ 判定到达目标集合的 foothold（没有集合信息时兜底：y 到了绳的另一端）
```

- **上下怎么判**：`zones.climb_direction` —— 看目标在绳的**上端**还是**下端**（绳的两头
  各压着哪条 foothold ⇒ 属于哪个集合）。说不清就返回 `None`，**宁可不做也不猜**。
- **两个判定参数**在 设置 → **判定参数** 页（跟着项目存），默认 6 px / 250 ms。
- **没有"要不要按跳"的开关**（2026-09-26 用户定：那是测试内容，不该进设置）——
  授权就是「命令前往」那一下：命令挂上就一路做到位（对齐 → 按跳 → 判到达）。
  ⚠ **感知层没有开关**（原来的 `route_enabled` 已撤，见 §7 末尾）：小地图定位一直跑，
  所以这里不用再考虑"感知关着时怎么办"。（平台识别那套已整块移除，同见 §7 末尾。）
- **攻击优先天然成立**：上绳任务挂在 tick 的 `else:`（前方无怪）分支里，
  攻击范围内有怪时根本到不了 ⇒「有怪先打、打完继续爬」不用额外写仲裁。
- **失败保护**（2026-09-26 用户要求）：**偏离绳梯**（横向偏出 18 px 且持续 0.6 s，
  硬编码）、从绳上掉下来（2 s 没回来）、超时（12 s）都算失败 ⇒
  **重新激活**（回到"重新对齐"重来，最多 3 次，到上限才放弃并记日志）——
  上绳本来就容易歪一下，重来比"停在那儿"有用得多；但**不能无限重来**（数据写错时
  会变成一直重试，看着像卡死）。
**下跳（`drop`）也已经做了**（2026-09-26）：

```
① 就近平齐到一个**可下跳 foothold**（边上那格 `footholds`，不填 = 起点集合的全部）
② **先按住 ↓**（0.25s，这一刻不按跳 —— 用户说的顺序是"按住↓再按跳"）
③ 按住 ↓ + 按跳，直到落到目标集合（或 y 比出发时大了 ≥40 —— 落地没圈成集合时兜底）
```

- 可下跳的 foothold 有好几个时**就近挑一个**（省得为一个点横穿平台）。
- 失败保护与上绳**同一套**（超时 / 失败重来，最多 3 次）；执行器也一样走
  `agent._climb_tick`（两种任务接口相同：`update/retry/cancel/attempt/max_attempts`）。
- 按键顺序是**分两步发**的（先只有 ↓、再 ↓+跳）：同一次 tick 里两个键一起发，
  游戏里未必算"先↓后跳"。

- **还没做**：`移动跳上绳`（跑动中卡时机 ⇒ 等跳跃标定）、Agent 在两种之间随机挑、
  以及「命令前往」把路线真发给执行器（P4 剩下的部分）。

**跳跃标定（前置，必须先做）**：录一段实机跳跃视频，量出
起跳初速度、重力、空中水平修正的响应延迟 → 得到「水平距离 / 高度差 → 起跳时机 + 按键时长」的查表。
❌ 在标定完成前，**不把视觉预测变成按键动作**（这是 `README.md`「视觉预测与决策边界」
和 `decision/agent.py` 模块注释里已经定下的纪律，继续遵守）。

**图上找路**（最后一步，不要提前做）：
横版地图的 foothold 连通图基本是**线性/树状**的，BFS 就足够，不需要 A* 调参。

### 11.3 两个必须记住的实测结论

1. ~~`mag = 4`（不是 16）~~ **【已更正，2026-09-25 晚】** 上一版把
   `miniMap/width,height` 当成了**底图像素尺寸**，又按 `mag=4` 换算 —— **两者都错**：

   - `miniMap/canvas` 导出来的 PNG 实际只有 **164×94**（不是 2630×1507）；
   - `width=2630 / 164 = 16.04` ≈ **16** —— 也就是说
     **1 底图像素 ≈ 16 世界像素**，**MapleNecrocer 硬编码的 `/16` 恰好是对的**；
   - 用绳梯做定量验证（把 7 根绳梯投影到底图上，采样那些位置的亮度）：
     `k=4`（我上一版用的）→ **全部越界、亮度 0**；`k≈16` → 亮度命中。
     视觉上也对上了：地形线压在底图平台的上沿、梯子顶端收在线上。

   所以正确做法是：**读底图 PNG 的真实尺寸**，用 `k = 世界跨度(=`width`) / 底图宽`
   反推（`core/mapdata.py` 的 `px_per_world` ✓）。`mag` 的含义**仍未查清**，
   先只做记录、不参与换算。
   残留问题：还有 **2~4 底图像素**的固定偏移（多半是 center 的口径或底图留边），
   用 `python -m tools.map_terrain_view 105090700 --dx N --dy N [--k K]` 人工拧准。
2. **小地图 canvas 很大**（这张图 2630×1507）→ 游戏窗口里显示的是
   「整张 canvas 缩放到面板」还是「1:1 裁剪」**还没验证** ✗ —— 这是 S3 的第一件事：
   抓一帧小地图，和 `105090700.png` 对照一次就能定。

   > **定于 2026-09-25（项目规范）**：这个方式**由用户人工选**（工作台
   > 「路线识别 → 小地图定位」，全局小地图 = fit / 局部小地图 = crop），
   > 每张图一份、存在 `datasets/map/<id>.mapcalib.json` 的 `mode`。
   > **不按匹配分自动判定、也不自动切换** —— 两种画法在不同图上确实不一样，
   > 分数高低说明不了该用哪种（要进游戏左右走两步看地形动不动才知道）。
   > `perception.minimap` 的 `diagnose` / `--watch` 一律沿用你选的那个
   > （`--mode saved`，默认）；匹配分只用来判断"这一次定位可不可信"。

   若为「缩放到面板」，则 世界→屏幕 = `(X + centerX) / mag × (面板尺寸 / canvas 尺寸)`，
   那个比例**每张图不同**（因为 canvas 尺寸不同），但可以由两个尺寸**算**出来，

## 12. 实施方案 v3（2026-09-26 定稿）

> 本节取代原 §6/§7 的分期与做法。**核心变化：不做自动分段、不做物理参数、只做"战斗区 + 回位"。**

### 12.1 已定决策

| 项 | 决定 | 理由 |
|---|---|---|
| 目标地图 | **`105090600`**（寺院通道2） | 正在跑自动的那张 |
| 阶段目标 | **战斗区 + 回位**：人工规定一组 foothold 作战斗区；玩家掉出去后沿**固定路径**回去 | 比"任意点导航"收敛得多，且不依赖物理参数 |
| 分段 | **不做自动分段** ❌ —— foothold 由人工在编辑器里分组 | 判定一律用"**脚下的 foothold id ∈ 集合**"，段只留作显示/辅助选择 |
| 集合存法 | 按地图 id 存 `{集合名: [foothold id…]}` —— **id 来自 WZ，重导地形也不失效** | 避免"段号会变"导致战斗区指错 |
| 未分组 foothold | **地形但无归属**（能站上去，但不属于任何集合，不参与路线） | |
| 集合之间的边 | **有向**；"怎么过去" = **「通行方式」**（见下）：`walk` 走 / `climb` 爬（绳梯）/ `jump` 跳 / `drop` 下跳 / `portal` 传送门（外加 `unconfirmed` 待确认） | 下落是单向的；"B 爬绳到 C"与"C 滑到 B"是两条 |
| 边的默认值 | **默认 `unconfirmed`（不可用）**；`walk` 由"同层判据"自动**建议**、人工确认 | 与 README「标定前不把视觉预测变成按键」一致 |
| 跳跃类 | **`jump`（跳）= 在 foothold 边缘按跳键**；**`drop`（下跳）= 按住 ↓ 再按跳**。按键不同、落点不同，是**两个类型**。**记录不受限，执行要标定** | 标定前不下发；先把位置标出来 |

**术语：通行方式**（2026-09-26 定名）—— 两个集合之间"**怎么过去**"，就是它们的**通行方式**。
编辑器里（`AddReachDialog`）问的就是这一件事：**终点 + 通行方式 + 它要求的东西（绳/门）**。

| 通行方式 | 界面上写 | 按键 | 还要指认什么 |
|---|---|---|---|
| `walk` | 走(walk) | 方向键 | — |
| `climb` | 爬（绳梯） | 上/下 + 方向 | **哪根绳**（`ladder`，如 `L3`） |
| `jump` | 跳(jump) | **站在边缘按跳键**（往前 / 斜着蹦） | — |
| `drop` | 下跳(drop) | **按住 ↓ 再按跳**（往下穿） | — |
| `portal` | 传送门 | 站上去 | **哪个门**（`portal`） |

⚠ **`jump` 和 `drop` 别混**（用户专门澄清过）：一个是"**在边缘按跳**"往前蹦，
一个是"**按住 ↓ 再按跳**"往下穿。两者都要用跳键 ⇒ **执行**前必须先做**跳跃标定**（§6）；
但**记录不受影响** —— 先把"这里要跳 / 要下跳"标出来，标定完就能跑。

### 12.2 「同层（可走）」的判据 —— 有实测支撑

> **两条 foothold 同层** ⟺ 存在一处接缝：x 区间**相接或重叠**（`gap = 0`）**且**接缝处高度差 **`Δy = 0`**。
> **集合 A 与 B 同层** ⟺ 存在一对 `(f∈A, g∈B)` 满足上式。

`105090600` 实测（85 条横向 foothold、399 处候选接缝）：

| 判据 | 判为"同层可走"的接缝数 |
|---|---|
| Δy=0 且 gap=0 | **70** |
| Δy≤2 且 gap≤2 | **70**（一样） |
| Δy≤2 且 gap≤8 | **70**（一样） |
| Δy≤10 且 gap≤20 | 84 |

⇒ **数据是双峰的**（要么严丝合缝、要么差得明显），**阈值不敏感** ✅
⇒ 差 3~10 / gap 3~20 的那 14 处 ⇒ **只作建议**，编辑器里高亮接缝并显示 `Δx/Δy`，人工确认
⇒ 附加防护：接缝附近（x±一个身位）若有**竖向 foothold 横跨该 y**（墙挡着）⇒ 不算可走

**两条实测结论（都是"判据看着对、实际判空"那种，值得留档）**

1. **绳端离平台差几十像素是常态**：`105090600` 实测 L1(x=56) 上端 44px、L2(x=701) 49px、
   L3(x=1245) 43px ⇒ 用 `ATTACH_PAD(24)` 当 y 容差时**每根绳的顶端都落空**，
   `climb` 边恒为 0 条（看着像"集合没圈对"）。
   ⚠ **但容差不能乱放**（当天就踩了一次）：把它放到 60px 之后，选「右下」（y=280 那块
   大平台）时**下面两根绳全亮了**（L2 顶端 231、L3 顶端 237，y 区间根本碰不到它；
   它们其实是「右下休息平台」的绳）。⇒ **两个问题两套判据**：
   · 「这根绳**属于谁**」（空间归属 → 编辑器高亮）= `ladders_of`，**严格**（±ATTACH_PAD）；
   · 「爬上它**能不能到上面**」（连通性 → 建议）= `ladder_ends` / `climb_suggestions`，
     **宽松**（绳端差几十像素也算）；
   · 「加爬升边时选哪根绳」= `ladders_touching`（上面两者的并集）。
2. **传送门的落点数据是有的**：`Portal.tm`（目标图号，`999999999` = 本图内）+ `Portal.tn`（目标门名）。
   但本图 8 个门里 **6 个是 `pt=0` 出生点**、2 个是**跨图**（`tm=105090500/105090700`）
   ⇒ 本图回位**一条 portal 边都不该有**（`portal_suggestions` 返回 0 条是对的，不是坏了）。
   `pt=0` 必须排除，否则会把出生点当成门。
