# 玩家行为打点（`core/behavior.py` → `behavior.log`）

**一句话**：把「角色做了什么、为什么停」按**事件**记成一行一行的日志，**人直接读**。

**初版范围（用户 2026-09-27 定的）**：**只打「玩家的任务」** —— 起跑 / 单步 / 完成 /
失败 / 叫停 / 没起跑。战斗、喝药、休息、死亡这些**后续逐渐扩展**（见文末清单）。

---

## 1. 为什么单开一份（和 `perf.log` 的分工）

`core/perf.py` 自己的说明第一句就写了：**"这是给「性能评估」用的，不是行为统计"**。
它的世界里只有 `n / 中位 / p95 / 最大` —— 回答"每帧花多久、链路抖不抖、资源涨不涨" ✓。

而"这一趟为什么停""断在第几步""后面还有几步没走"这类问题：

- 混在性能统计块里**读不出来**（那些数字没有主谓宾 ✗）；
- 真塞进去就会把 `perf.log` 的性质带偏（它要能一眼看出**性能**退化 ✗）。

⇒ 所以**单开一份**：`perf.log` 管性能、`behavior.log` 管行为。两者**不互相引用**，
也**不同一个开关**（见 §4）。

**分工线（用户 2026-09-28 定的终版）**：

- `behavior.log` = **所有「行为 / 状态」**：任务下达、战斗、寻路、爬绳、**角色状态**、
  防掉线休息、定时行为……（原话："任务下达、战斗、寻路、角色状态等等打点应该在
  behavior.log 里" ✓）；
- `perf.log` = **只管 GUI / 推流收流 / 性能**（原话 ✓）：fps / 预算 / 探针延迟 / 资源 /
  小地图成败（`live_thread`）、发键链路耗时（`input.send*`）、输出节拍（agent 的
  `*_gap_ms` / `*_round` / `climb_tick`）✓。

⚠ **迁移史**：`route_* / climb_* / goto_* / replan* / afk_* / key_* / player_* /
zone_* / mob_goto_* / jump / out_evade / st_*` 这批原来是"借"在 `perf.log` 里的
`perf.count` / `perf.note` / `perf.sample` —— **2026-09-28 全迁到 `behavior.log` 了** ✓
（离散的走 `event`、每拍状态走 `sample` 节流），`perf` 里不再有它们 ✗。

## 2. 格式（这就是全部可读性的来源）

一行一个事件，**时间戳（含毫秒）+ 事件名 + `key=value`**，值与值之间**两个空格**：

```
2026-09-27 11:16:37.887  task_plan_fail dst=左上平台  why=实时线程还没把「路径解析器」交给我 —— 先在「实时」页开始，命令才发得出去
2026-09-27 11:16:37.888  task_start     steps=2  why=命令前往：丙平台
2026-09-27 11:16:37.888  task_step      note=走过去：「乙平台」（1 个落点，就近）  secs=0.0  step=1/2
2026-09-27 11:16:37.888  task_fail      left=0  reason=爬到 y=100 就不再升了（3.0s 没变好）：还差 200 px  secs=0.0  step=2/2
2026-09-27 11:16:37.889  task_cancel    secs=0.0  step=1/1  why=关自动
2026-09-27 11:16:37.889  task_done      note=…  secs=0.0  steps=1
```

约定：

- **key 一律英文**（好 `Select-String` / `grep` ✓），**value 保留人话**（直接看得懂 ✓）；
- 字段**按 key 排序**写（同一种事件每次长得一样，扫一眼就知道有没有缺 ✓）；
- **缺的字段不写**（`secs` 拿不到就整段不出现 —— 不许写 `secs=None` 这种噪音 ✗）；
- **值里的换行被压成空格**（一行一个事件是这份日志的底线 ✗）。

## 3. 初版事件表 + 接线点

**接线点只有四处**（都在 `decision/agent.py`，一处不会漏 ✓）：

| 事件 | 谁打 | 关键字段 | 语义 |
|---|---|---|---|
| `task_plan_fail` | `_plan_fail()`（`plan_and_start_route` 的**唯一**失败出口）| `dst` / `why` | **压根没起跑**：没注入解析器 / 解析不出 / 造任务出错 |
| `task_start` | `start_route()` | `why` / `steps` | 一条多步路线起跑（「命令前往」/「定点休息」/ 区域归位都走这里 ✓）|
| `task_step` | `_task_finished()` 的"接着走下一步"支 | `step` / `secs` / `note` | **刚走完的是第几步**（`step` 取 +1 **之前**的值 ✓）|
| `task_done` | `_task_finished()` 的收尾 | `steps` / `secs` / `note` | 整条走完（**单步路线也走这里** ✓）|
| `task_fail` | `_task_finished(failed=True)` | `step` / `secs` / `left` / `reason` | 某一步失败 ⇒ 整条停掉；`left` = 后面还有几步没走 |
| `task_cancel` | `stop_route()` | `why` / `step` / `secs` | 被叫停（关自动 / 手动 / 休息结束…）|

两个细节（都是踩过才写下来的）：

- `task_cancel` 有**前提**：`self._climb is not None or self._route` —— `stop_route` 在
  "关自动"那条早退里**每拍**都会被调一次（空停 ✓），不加前提会把日志刷满 ✗；
- `secs` = `_step_secs()`，用 **`_climb_started`** 当起点 ⇒ **进战斗那几秒不算**
  （它会被 `_climb_interrupted` 重打 ✓）—— 这是"玩家眼里的用时"，不是墙上时间 ✓。

### 3.1 任务**内部**变化（2026-09-28 用户要求："寻路的各类变化也做进行为打点"）

`task_*` 只回答"走到第几步、整条成没成"；而"卡在哪、为什么断"要看**这一步里面**发生了什么。
所以再加三类，接线点只有**一处**：`agent._mark_route_change(job)`（在 `_climb_tick` 里
`job.update` 之后调一次 —— 它检测任务对象自己的状态**跳变**，只在变化那一刻记一条，
不是每拍 ✗）：

| 事件 | 谁打 | 关键字段 | 语义 |
|---|---|---|---|
| `route_phase` | `_mark_route_change` | `ladder` / `prev` / `to` / `note` | 任何任务的 `phase` 变了（`align→climb`、`climb→align`、`climb→done`…）；`note` 是任务当时那句人话 ✓ |
| `route_diag` | `_mark_route_change` | `ladder` / `what` / `note` | 爬绳的**斜跳**：`what=起跳` / `what=结束·吸上绳` / `what=结束·没吸上` ✓ |
| `route_retry` | `_mark_route_change` | `ladder` / `attempt` / `note` | 一次尝试**失败重来**（`attempt` 涨到几）|

实测一行长这样（人直接读得懂）：

```
route_diag     ladder=L2  note=斜跳上绳：离绳 80 px（区间 20~120…）⇒ 按住 → + 按跳  what=起跳
route_diag     ladder=L2  note=已上绳：按住 ↑ 往上爬（到 y ≤ 100 算到）  what=结束·吸上绳
route_phase    ladder=L2  note=已上绳：按住 ↑ 往上爬…  prev=align  to=climb
route_retry    attempt=2  ladder=L2  note=第 2 次尝试：重新对齐 L2
route_phase    ladder=L2  note=到达：位置状态广播「已到 L2 上端」  prev=align  to=done
```

⚠ 打点专用状态（`_bc_*`）挂在 agent 上、**惰性初始化**：任务对象一换就重置基线，不把上一个
任务的状态带过来 ✗；字段全走 `getattr` 兜底（走/跳任务没有 `_diag_flying`/`attempt` ⇒ 当
`None`/False），别因为字段名不同就把打点弄崩 ✗。

### 3.4 日志量：**两类量要分开节流**（2026-09-28 用户要求降噪 ✓）

用户看着 760 KB 的日志说"**为什么不就在 `behavior.log` 里精简打点**"⇒ 对 ✓ —— 这次就是
**在写日志这一侧**动手（`sample` 本来也写这个文件 ✓，不是换地方 ✗）。实测 7615 行的构成：

| 事件 | 占比 | 处理 |
|---|---|---|
| `task_start` + `task_done` + `task_step` | **55.8%** | 其中 **~45% 的任务 1 秒内就完成** ⇒ **合并成一条** `task_quick` ✓ |
| `chase_dist` / `climb_y` / `climb_dx` | ~20% | 它们是**连续量**（每拍都在变）⇒ **定频 `min_gap=1.0`** ✓ |

**① 连续量 ⇒ `min_gap`（定频）**：`sample` 原来的节流是"**值变了就记**" —— 对**每拍都在变**
的量（距离、坐标）**等于不节流** ✗（实测 `chase_dist` **20~25 ms 一条** ✗）。现在给它们传
`min_gap=1.0` ⇒ **两条之间至少隔 1 秒**，不管值变不变 ✓（1 秒一个点，看趋势够用 ✓）。
⚠ **离散状态**（`climb_y_held` / `climb_phase` / `climb_on_ladder`）**不要**给 `min_gap` ✗
—— 它们要的是"**跳变了立刻记**"（0→1 那一拍最要紧 ✓）。⚠ 第一拍**总会**记一条（曲线要有
起点 ✓）。

**② 瞬时任务 ⇒ 合并成 `task_quick`**：`task_start` 走 `behavior.task_open` ⇒ **先暂存**
（这一拍不落盘 ✓），1 秒内就收工的交给 `task_settle` ⇒ **合成一条** `task_quick`
（带上起跑那句 `why` ✓）；跑得久的 ⇒ 起跑那条**按原时间戳补上**（`_flush_pending` ✓，
由每次打点顺手触发 ✓）。
⚠ 代价（用户已确认 ✓）：起跑那条**最晚 1 秒落盘** ⇒ 进程若在这 1 秒内挂掉，**最近那一条
`task_start` 会丢** ✗ —— 这是"一行一次落盘"那条纪律**唯一的例外** ✓。
⚠ `task_fail` / `task_cancel` **必须传 `merge=False`** ✗：被叫停 / 失败**不是"走完了"**，
伪装成 `task_quick` 会误导 ✓。
⚠ 命名别混：**函数 `task_open`**（暂存待写的起跑行）vs **事件 `task_begin`**（"挂上这一步的
执行器"，在 `start_climb` 里 ✓）✓。

### 3.5 ⭐ 定频快照：`pos` / `act` / `drink_hp`（用户 2026-09-28 要求 ✓）

**为什么加**：2026-09-28 现场"卡了 2 小时 22 分"（定点休息去「右下休息平台」走不到），
日志里**只有** `climb_dx` / `climb_y` 两条探针 ⇒ 只能回答"人在哪（离绳 400px）"，
**回答不了"有没有在按方向键"** ⇒ **分不出**这两件：

- 「**人动不了**」= 一直按着方向键、位置不变（死了 / 卡死 / 倒地）；
- 「**系统没发键**」= `move=0`、`keys` 空、位置不变（决策 / 对齐逻辑卡住）。

⇒ 两条快照**一对**就分开了 ✓。

| 事件 | 字段 | 频率 |
|---|---|---|
| `pos` | `x` / `y`（**世界坐标** ✓）/ `sets`（**当前所在集合** ✓）/ `hp`（0~1）/ `st`（状态名） | **1 秒一条**（定频） |
| `act` | `move`（这一拍任务给的方向 -1/0/+1）/ `keys`（这一拍按着的键）/ `task`（任务相位，如 `align`） | **1 秒一条**（定频） |
| `drink_hp` | `hp`（**触发那一刻**的血）/ `thr`（阈值） | 每次喝血药（**不节流** ✓） |

⚠ **并成两条而不是三四条**：日志体积。一秒一条 ≈ **0.7 MB/小时**；拆成三四条就是两三倍 ✗。

⚠⚠ **接线点必须挂在 tick 的"休息分支之前"**（`if self.state in REST_STATES:` 前面 ✓）：
上面那次卡住的状态恰恰是「定点休息」的 `afk_spot_walk`（**属休息分支** ✓）⇒ 挂在常规路径上
会**一条都打不出来** ✗（用例 `t_snap_beat` 整段摆在 `afk_spot_rest` 里跑，挂错位置当场红 ✓）。

⚠ `move` 只能由 `_steer` 写（**唯一**设方向的地方 ✓）；`_snap_beat` **读完清零**（不清 ⇒
"没动的那几拍"会残留上一次的方向 ✗）。⚠ 快照打到日志里的其实是**上一拍**的动作（它挂在 tick
靠前 ✓），差一拍（≈16ms），1 秒粒度下无所谓 ✓。
⚠ 打点失败一律吞掉（不许影响决策 ✓ 同其它打点 ✓）。
实现：`decision/agent.py::_snap_beat`；喝药那条在 `_drink_potions` 里 ✓。

## 4. 取舍（改这块之前先看）

| 选择 | 为什么 |
|---|---|
| **一行一次落盘**（不攒批）| 事件本来就稀疏（一趟任务几条），而"卡住前最后那几条"恰恰最想看 —— 攒在内存里它们可能**永远写不出去** ✗（2026-09-27 那次"卡了之后日志里什么都查不到"就是这类教训）。将来事件变密（战斗/挨打那种）再改按时间攒一批 —— **只动 `_write()` 一处**，格式不变 ✓ |
| 开关**跟 `perf_log` 共用** | 初版不加新参数（用户没要求）；将来要分开 = 加一格 + `live_thread` 两行 ✓ |
| **不加锁** | 调用点都在**实时线程**那一条（GUI 只读不写）—— 和 `perf` 同一条纪律；将来有人从别的线程打点，**先补锁** ✗ |
| 写失败**吞掉**（不抛）| 打点把主流程搞挂是最不能接受的 ✗（同 `perf`）|
| 文件有上限（`MAX_BYTES`，超了砍前半截）| 和 `perf.log` 同一套；**别调小**（教训同 `perf.MAX_BYTES`：日志一裁，出事的起点就查不到了 ✗）|

## 5. 怎么用它（实战口径）

1. **"刚才为什么停了"** ⇒ `Select-String -Path behavior.log -Pattern 'task_fail' -Context 0,0 | Select-Object -Last 5`
   —— `reason` 就是界面上那行 note（同源 ✓）、`step`/`left` 说清断在哪、还剩几步；
2. **"它到底起跑过没有"** ⇒ 看有没有 `task_start`：只有 `task_plan_fail` = 根本没动
   （解析不出路线，问题在**地形/集合**那边，不在执行器 ✗）；
3. **"是不是我把自动关了"** ⇒ `task_cancel` 的 `why` 直接写着（`关自动` / 用户点的那句 ✓）；
4. **"这个项目一趟任务一般多久"** ⇒ `task_done` 的 `secs`（**有效**用时，打架那几秒不算 ✓）。

## 6. 后续扩展清单（**只加事件名，不动格式** ✓）

按优先级（谁最常被问谁先做）：

| 事件（拟） | 要回答的问题 | 在哪打 |
|---|---|---|
| `fight_kill` / `fight_hit` | 这一波打了几只、挨了几下 | `agent` 的 attack 分支 + `hp` 下降沿 |
| `pot_hp` / `pot_mp` | 什么时候喝的药、喝的时候血多少 | `_output_actions` 的喝药那两支 |
| `rest_enter` / `rest_done` / `rest_interrupt` | 休息了几次、多久、为什么提前收工 | `_run_rest` / `_finish_rest`（`perf` 那几个 `afk_*` 的"人话版"）|
| `death` / `revive` | 死过几次、死在哪 | 玩家框/小地图"认不出黄点"那几条（见 `player_gone` 注记 ✓）|
| `manual_on` / `manual_off` | 手动输入开了多久 | 玩家面板的手动开关 |
| `reconnect_*` | 断线重连走过哪几步 | `decision/reconnect.py` |
| `timer_fire` | 自定义定时行为触发了几次 | `_custom_timers` |

**口径**：新事件一律"**一行、key=value、缺的不写**"，并在
`tools/selftest_behavior.py`（格式）或 `selftest_decision.py`（接线）里钉一条 ✓。
