# 自动标注性能探究（GPU 能不能加速 / 该先做什么）

> 这份文档记录一次**实测**的结论，目的是以后不用重跑一遍：自动标注（模板匹配）
> 能不能用 GPU 加速、值不值得做、以及有哪些更便宜的路。
> 数据都是在本机（B 机）上量出来的，命令与参数写在文末「怎么复现」。
>
> 标记沿用本项目惯例：✅ 实测确认 / ⚠ 待验证或有代价 / ❌ 明确不做。

---

## 1. 一句话结论

**能上 GPU，但这条链路不划算 ❌** —— 朴素 torch 版只比「现在的多进程 CPU」快约 2×，
而同期有一个**改动小得多**的 CPU 优化：**改用灰度匹配，快 2.6×** ✅。

| 方案 | 单帧耗时 | 相对现在（19 进程） | 结论 |
|---|---|---|---|
| 现在：CPU 单进程（BGR 匹配） | 27.7 s | — | 基线 |
| **现在：CPU 19 进程并行** | **≈1.46 s** | 1× | 148 帧 ≈ **215 s** |
| GPU 原型：torch 逐模板卷积 | 0.75 s | 2.0× | ❌ 收益配不上复杂度 |
| GPU 原型：按尺寸分组批量卷积 | 0.73 s | 2.0× | ❌ 同上（批处理没救回来） |
| **CPU：模板+画面都走灰度** | **10.5 s** | **2.6×** | ✅ 推荐（要留开关，见 §5） |

（口径：单帧 1920×1080、2 只怪 → 54 个模板含镜像；项目参数 `scale=1.406`、
`downscale=1`、`thr=0.90`、`dist=0.06`、`per_mob=20`、`peaks=3`。）

---

## 2. 机器与环境（决定了"哪条 GPU 路能走"）

| 项 | 实测 | 影响 |
|---|---|---|
| GPU | **RTX 5070** | 有卡 ✅ |
| torch | **2.11.0+cu128**，`cuda.is_available()=True` ✅ | torch 这条 GPU 路可用 |
| OpenCV | **5.0.0（pip 版）**，`cv2.cuda.getCudaEnabledDeviceCount()=0` ❌ | **`cv2.cuda` 这条路直接封死**：pip 轮子不带 CUDA，想用只能自己编译 OpenCV ❌ |
| CPU | 20 核（进程池用 `cpu_count()-1 = 19`） | 现在的并行度已经吃满机器 |

⚠ 顺带量到的固定成本：**PNG 解码 30 ms/帧**（GPU 也躲不掉）。相对 27.7 s/帧 只占
0.5%，所以"优化匹配"这件事是有意义的 ✅ —— 瓶颈确实在匹配上。

---

## 3. GPU 那条路：数学是对的，但没吃到便宜

**先证明"能做到"** ✅：用 torch 卷积复算 `cv2.matchTemplate(TM_CCORR_NORMED, mask=)`
（就是把 `Σ M·T·I / sqrt(Σ M·T² · Σ M·I²)` 写成两次 `conv2d`），和 OpenCV 逐像素比：

```
最大逐像素差 5.3e-06 ~ 6.6e-06        ← 纯浮点误差，同一个公式 ✅
峰位一致（同样的 top-1 分数与坐标）   ✅
```

**再量"划算吗"** ❌：

- 逐模板：**13.9 ms/模板** → 54 个 ≈ 0.75 s/帧；
- 按尺寸分组批量卷积（16 组，组内一次 conv）：**0.73 s/帧**，几乎没变。

为什么批处理没救回来 ⚠：模板核很大（~86×86 起）、画面是单通道但尺寸大，
`conv2d` 在 cuDNN 里挑到的算法很差 —— 粗算算术量约 3 TFLOPs，5070 的理论时间
约 0.1 s/帧，实测 0.73 s（差 7 倍）。**要压到 <0.3 s/帧 才值得做**
（那样才比 19 进程快 5 倍以上），得上 **FFT 相关**或整帧批处理 ⚠ —— 本次**没有验证**，
因为即使做到，收益也只是相对"CPU 19 进程"的个位数倍，而代价是重写匹配核心 ❌。

---

## 4. 黑色区域乱标：已确认修好 ✅

顺手拿真实帧验了上一轮那个 bug（`_masked_energy` + `min_energy_ratio` 的能量比闸门）：
一帧 5 个框，**各框处的灰度均值是 57 / 90 / 103 / 149 / 161** —— 全在真实画面内容上 ✅。
黑边/纯色面板会是 10~30 量级，一个都没有 ✅。（判据细节见 `tools/detect_mobs.py`
的 `_masked_energy` 注释。）

---

## 5. 推荐：先把这两件便宜的做掉 ✅

### 5.1 灰度匹配（2.6×，推荐）

模板和画面都转灰度再匹配，**实测快 2.6×**（27.7 → 10.5 s/帧，148 帧 215 s → ≈83 s）✅，
且**检出的是同一批框** ✅：同样 5 个框、同样的模板、位置差 ≤1 px
（例：BGR 框中心 (959,898) ↔ 灰度框左上 (925,857) + 69×84 尺寸，换算完全一致）。

⚠ 代价（必须知道）：灰度丢掉颜色信息。**靠颜色才能区分**的画面（同形状不同颜色的怪、
颜色不同但灰度相近的地形）可能变化 —— 本次数据上没差，但这是**精度取舍**，
所以建议做成**开关**（默认灰度，保留彩色），并配一条自检：同一帧两种模式检出框做 IoU
比对，差异大就报出来 ⚠（**尚未实现**）。

### 5.2 其它线性收益（按需，都有代价）

| 手段 | 收益 | 代价 |
|---|---|---|
| `downscale` 1 → 2 | 约 4× | 远处小怪/小位移的精度；本项目的怪在 1080p 下 ds=2 通常仍够 |
| 限定 `region` 搜索区 | 与面积成正比 | 目标只在区域内被找到，出界就漏 |
| 减少 `per_mob` | 线性 | ⚠ 代码注释里写明了会漏掉某些动作相位（"看不见的洞"） |
| 更多进程 | 已吃满 19/20 核 | 没空间 |

---

## 6. GPU 的正确用法是换路线 ⚠

伪标注 → 训练 YOLO → 推理。`tools/auto_label.py` 开头就写了这是原定方向 ✅：
到时"用不用 GPU"是顺带的事（YOLO 推理天然在 GPU 上），而模板匹配那套只留在
"没有模型 / 冷启动"阶段。**所以模板匹配阶段不值得为 GPU 重写** ❌。

---

## 7. 怎么复现

```powershell
# 环境
python -c "import torch,cv2;print(torch.__version__, torch.cuda.is_available(), cv2.cuda.getCudaEnabledDeviceCount())"

# 基线：单帧耗时与检出（用项目里存的那组参数）
python -m tools.detect_mobs --mobs 3230100,4230101 --sprites datasets/sprites/mob ^
    --frames projects/猴林迷宫I/frames --out <临时目录> --scale 1.406 --downscale 1 ^
    --thresh 0.9 --min-distinct 0.06 --per-mob 20 --limit 1 --workers 1
```

量 GPU 原型时的要点（临时脚本，未保留）：把 `Σ M·T·I` 与 `Σ M·I²` 各写成一次
`torch.nn.functional.conv2d`（掩码当核），除 `sqrt` 即可；先按模板尺寸分组，
组内 `stack` 成 batch 再做 —— 但要先看 §3 的结论再决定投不投入 ⚠。
